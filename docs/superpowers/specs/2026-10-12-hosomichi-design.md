# ほそみち — 設計書

日付: 2026-10-12

## 目的

散歩・探検のためのルート案内。出発地から目的地まで、遠回りの上限の範囲内で、道幅の狭い道（路地・小道・階段など）をなるべく多く通るルートを出す。スマホのブラウザで地図を見ながら歩くことを想定する。

やらないこと: 周回ルート、曲がり角ごとの案内・音声案内、地名検索、車・自転車向けの案内、5km超のルート。

## 技術

- 場所: `ranzo_project/hosomichi`
- Vite + 素のJS + pnpm、dev server は port 5790
- 地図: Leaflet + OSM タイル
- 道データ: Overpass API（開発時は Vite proxy、本番は Vercel 関数 `api/overpass.js` を GET で経由）
- テスト: Vitest
- 公開: Vercel（GitHub 連携で push 時に自動デプロイ）

## 1. 狭さ点数

道（OSM way）ごとに狭さ点数 n（0〜1、1が一番狭い）と根拠（`measured` = 実測 / `estimated` = 推定）を付ける。

### `width` タグがある場合（実測。種別より優先）

数値部分を m として読む（`"3"`, `"3 m"`, `"2.5"` など）。読めない場合は「タグなし」として扱う。

| 幅 | n |
|---|---|
| 2m 以下 | 1.0 |
| 2m 超〜4m 以下 | 0.75 |
| 4m 超〜6m 以下 | 0.4 |
| 6m 超 | 0.1 |

### `width` タグがない場合（種別から推定）

上から順に評価し、最初に当てはまった値を使う。

| 条件 | n |
|---|---|
| `footway=sidewalk`（大通り沿いの歩道） | 0.05 |
| `service=alley`、`highway` が `steps` / `footway` / `path` / `cycleway`（`foot` が `yes`/`designated` の場合のみ） / `track` | 0.9 |
| `highway` が `living_street` / `pedestrian` | 0.75 |
| `highway=service`（`alley` 以外） | 0.6 |
| `highway` が `residential` / `unclassified` / `road` | 0.5 |
| `highway` が `tertiary` / `tertiary_link` | 0.2 |
| `highway` が `secondary` / `primary` / `trunk` とその `_link` | 0.05 |

### 除外する道（グラフに入れない）

- `highway` が `motorway` / `motorway_link`、`construction`、`proposed`、上の表にない値
- `access` が `private` / `no`（ただし `foot` が `yes` / `designated` / `permissive` なら通れる）
- `foot=no`
- `cycleway` で `foot` が `yes` / `designated` でないもの
- `area=yes`（広場の外周線など）

## 2. ルートの選び方

1. 出発地と目的地の直線距離が 5km を超える場合は、データを取得せずにエラーにする。
2. 取得範囲 = 出発地と目的地の外接矩形に、直線距離の20%（最低300m）の余白を四方に足したもの。
3. 取得範囲を固定の 0.03 度グリッドのタイルに分け、ブラウザが `/api/overpass?tx=&ty=` で1枚ずつ（同時2本まで）取得する。サーバは Overpass から `highway` way とその node を取り、使うタグだけ残したコンパクト形式で返す。ブラウザは全タイルを結合して重複を除き、無向グラフを作る。Vercel の関数応答は 4.5MB が上限で、5km のルートの範囲を一度に取ると超えるため。タイルが固定なので CDN キャッシュも効き、プロキシが返せるのは1リクエストにつき1タイルだけになる。辺 = way 上の隣り合う node の組。辺は長さ（m）、n、根拠を持つ。
4. 出発地・目的地は、グラフ上で一番近い node に吸着させる。どちらかが 200m 以内に node を持たない場合はエラーにする。両方が同じ node に吸着した場合もエラーにする。
5. 辺のコスト = 長さ ×（1 + α ×（1 − n））。α = 0, 0.5, 1, 2, 4, 8, 16, 32 の8通りでダイクストラ法を回す。
6. α = 0 の結果を最短ルートとする。最短ルートの長さを L0、遠回りの上限を r（1.2 / 1.5 / 2.0 から選択。初期値 1.5）とする。
7. 長さが r × L0 以下のルートのうち、狭い道（n ≥ 0.7）の長さの割合が最大のものを採用する。同率なら短い方。α = 0 は必ず条件を満たすので、採用ルートは必ず存在する。
8. 出発地と目的地がつながっていない場合は「ルートが見つかりません」というエラーにする。

### 表示する数字

- 狭い道の割合（採用ルートと最短ルートの両方）
- 遠回りの倍率（採用ルートの長さ / L0）
- 距離（km）
- 幅の根拠の内訳（採用ルートの長さのうち、実測の割合と推定の割合）

## 3. 画面

スマホ縦向きを前提にした1画面構成。地図を全面に置き、下に引き出しパネルを置く。

1. 起動時は現在地を中心に地図を表示する。位置情報が拒否・失敗した場合は東京駅（35.6812, 139.7671）を中心にする。
2. 出発地の初期値は現在地。地図を長押し（PCでは右クリック）すると「ここを出発地に / ここを目的地に」を選べる。
3. パネルで遠回りの上限（1.2 / 1.5 / 2.0倍）を選び、「ほそみちで行く」を押す。目的地が未設定のときはボタンを無効にする。
4. 採用ルートを狭さで色分けした線で描く（n が高いほど濃い色）。最短ルートは比較用に灰色の点線で重ねる。
5. パネルに第2節の数字を表示する。
6. `watchPosition` で現在地の点を更新する。「現在地に戻る」ボタンを置く。

### エラー表示

| 状況 | 表示 |
|---|---|
| 直線距離が 5km 超 | 「5km以内で選んでください」 |
| Overpass が失敗（別エンドポイントでの再試行も失敗） | 「地図データを取得できませんでした。少し待って再試行してください」 |
| 出発地の 200m 以内に道がない | 「出発地の近くに歩ける道がありません」 |
| 目的地の 200m 以内に道がない | 「目的地の近くに歩ける道がありません」 |
| 出発地と目的地が同じ node に吸着した | 「出発地と目的地が近すぎます」 |
| 現在地が取れず出発地も未設定 | 「出発地を選んでください（現在地が取れていません）」 |
| つながっていない | 「ルートが見つかりません」 |
| 採用ルート = 最短ルート | ルートは表示し、「この範囲では狭い道を増やせませんでした」と添える |

## 4. 構成

`src/lib` は DOM に触れない純粋関数にする。

| ファイル | 役割 |
|---|---|
| `src/lib/narrowness.js` | OSM タグ → `{ n, source }`、または除外なら `null` |
| `src/lib/geo.js` | 距離（haversine）、取得範囲の計算、5km 判定 |
| `src/lib/graph.js` | Overpass の応答 JSON → 無向グラフ（除外ルールを適用） |
| `src/lib/dijkstra.js` | 重み関数を受け取る最短経路（二分ヒープ） |
| `src/lib/route.js` | 最寄り node への吸着、αを8通り試して採用ルートと最短ルートを返す |
| `src/lib/stats.js` | 狭い道の割合、遠回りの倍率、距離、根拠の内訳 |
| `src/lib/segments.js` | ルートを狭さの帯（狭い/中間/広い）ごとの線に分ける |
| `src/lib/format.js` | 数字の表示形式とエラー文言 |
| `src/lib/tiles.js` | 取得範囲 → 固定 0.03 度グリッドのタイル、タイル番号 → 範囲 |
| `src/lib/overpassQuery.js` | Overpass クエリの組み立て、タイルパラメータの検証、コンパクト形式の変換と結合（ブラウザとサーバで共有） |
| `src/overpass.js` | ブラウザ側の取得（範囲をタイルに分け、同一オリジンの `/api/overpass?tx=&ty=` を同時2本まで GET して結合） |
| `api/_overpass-upstream.js` | サーバ側で Overpass を叩く（ミラーを順に試す）。Vercel 関数と Vite の dev middleware で共有 |
| `api/overpass.js` | Vercel 関数。タイル番号（tx,ty）を受け取り、クエリはサーバ側で組み立てて、コンパクト形式で返す |
| `src/map.js` / `src/panel.js` / `src/main.js` | 画面の配線。`window.__app` を公開してヘッドレスで検証できるようにする |

## 5. テスト

- `narrowness`: 代表的なタグごとの値、`width` が種別より優先されること、`width` の書式ゆれ、除外ルール
- `geo`: 距離、取得範囲の余白（20% / 最低300m）、5km 判定
- `graph`: 小さな Overpass 応答から辺の数・長さ・n が正しく作られること、除外 way が入らないこと
- `dijkstra`: 手で作った小さなグラフで正しい経路が出ること、つながっていないときに `null` を返すこと
- `route`: 不変条件をランダムな格子状の街（乱数シード固定・多数）で総当たりで確認する
  - 採用ルートの長さ ≤ r × L0
  - 採用ルートの狭い道の割合 ≥ 最短ルートの狭い道の割合
  - α = 0 の結果が最短ルートと一致する
- 実データ: 谷中付近の Overpass 応答を fixture として保存し、採用ルートの狭い道の割合が最短ルートより高いことを確認する

## 6. 動作確認

ブラウザのプレビューで谷中付近の出発地・目的地を `window.__app` から設定してルートを出し、表示された数字と線をスクリーンショットで確認する。
